# Go Back — Production Readiness Plan

**Status:** Beta; production release is not approved yet.  
**Branch:** `release/production-readiness`  
**Baseline audited:** `main` at `ae52d45d03efd7f4e0cdc0effb519b85b21fbd65` (2026-10-21).

This document is the release gate for turning Go Back into a dependable, privacy-respecting Android app. A successful CI run or a generated APK is necessary, but not sufficient, for production readiness.

## Current baseline

- React Native + Expo SDK 54 + TypeScript; Android native behavior is generated by Expo prebuild/config plugins.
- Core planning features use local SQLite; optional system features include UsageStatsManager, AccessibilityService-based blocking, and home-screen widgets.
- CI currently runs Expo prebuild, TypeScript checking, and Jest tests. Recent runs on 2026-10-21 passed.
- There are currently three overlapping APK-related workflows (`android-apk.yml`, `android-build.yml`, and `beta-release.yml`). Release outputs and version metadata are duplicated and some filenames/version strings are hard-coded.
- The current app is publicly described as beta. The repository itself identifies accessibility heuristics, background timers/notifications, widget behavior, and backup encryption as unresolved areas.
- The repository has no license file. Resolve licensing before public distribution/reuse.
- Android application ID is `com.goback.focus`; current app config has version `1.0.0` and Android versionCode `1`. Do not change the application ID after public distribution without an explicit migration plan.

## Workstreams and release gates

### P0 — Release integrity and reproducibility

- [ ] Choose one canonical Android release workflow; eliminate duplicate release publication and ambiguous APK artifacts.
- [ ] Use a committed lockfile and `npm ci` in CI/build workflows; avoid dependency drift from `npm install`.
- [ ] Set explicit minimum Node/Java/Android SDK/Gradle toolchain versions and workflow permissions.
- [ ] Make the version and Android versionCode a single source of truth; fail CI if they disagree.
- [ ] Separate internal/preview builds from signed production builds.
- [ ] Configure secure signing credentials as repository/environment secrets; never commit keystores/passwords.
- [ ] Produce deterministic release notes, SHA-256 checksum, build metadata, and source commit reference.
- [ ] Add dependency vulnerability/licence checks and pin third-party GitHub Actions to reviewed immutable revisions where practical.
- [ ] Verify all exported artifacts are release builds, not debug/test-signed artifacts.

**Gate:** clean build from a fresh checkout, CI green, artifact checksum verified, package/version verified, production signing key securely configured, release can be reproduced from a tagged commit.

### P0 — Data safety, backup, and migrations

- [ ] Audit SQLite schema initialization and migrations for upgrades from every published beta schema.
- [ ] Add tests for migration ordering, partially applied migrations, invalid rows, and failed writes.
- [ ] Audit backup import with malformed JSON, oversized files, duplicate IDs, unknown schema versions, invalid dates/types, and missing fields.
- [ ] Make restore transactional: reject invalid input without partially overwriting local data; show a preview/confirmation and clear success/failure messages.
- [ ] Document plainly that JSON backups contain personal data and are currently unencrypted.
- [ ] Decide whether to implement encrypted backups before production. If yes, define key derivation/storage and recovery UX; never claim encryption until tested.
- [ ] Confirm destructive actions have clear confirmation and there is no accidental deletion on cancel/failure.
- [ ] Test restart/reinstall/upgrade behavior and backup round trips on device.

**Gate:** migration and backup/restore tests pass, invalid imports are non-destructive, user-facing privacy/backup explanation is accurate.

### P0 — Android system features and permission transparency

- [ ] Test focus timer through backgrounding, screen lock, force-stop, process death, reboot, Doze/battery optimization, permission denial, and notification channel changes.
- [ ] Verify timer state is derived safely from persisted timestamps, does not drift or double-complete, and recovers after process death.
- [ ] Test notification permission denied/granted and scheduling/rescheduling behavior across supported Android versions.
- [ ] Audit AccessibilityService declaration and behavior. Explain exactly what visible text it inspects, that processing is local, and why the permission is required before the user opens Android Settings.
- [ ] Test each blocking rule against false positives, false negatives, feed previews, playback controls, navigation changes, app updates, and accessibility trees from multiple versions of YouTube/Instagram.
- [ ] Ensure disabling a rule/service immediately stops blocking and provide a reliable emergency/escape path.
- [ ] Never describe Shorts/Reels/channel matching as guaranteed; third-party accessibility labels are not stable contracts.
- [ ] Test UsageStats permission flow, empty results, date boundaries/time zones, revoked permission, unavailable apps, and Android version differences.
- [ ] Test every widget's deep link/navigation route and home-screen launcher behavior across different launchers and resizes.
- [ ] Test on multiple real Android devices/OS versions, not only Expo prebuild or an emulator.

**Gate:** permission flows are comprehensible, failure states are safe, critical paths pass real-device testing, experimental features remain labelled as such until measured and stable.

### P1 — Product quality, accessibility, and reliability

- [ ] Add component/service tests for tasks, notes, syllabus, exams, focus timer, habits, goals, search, theme settings, and backup flows.
- [ ] Add regression coverage for navigation/deep links, empty states, loading states, failed storage operations, and concurrent rapid taps.
- [ ] Review font scaling, screen readers, semantics/labels, minimum touch targets, contrast, keyboard/focus behavior, reduced motion, and landscape/small-screen layouts.
- [ ] Review date/time handling for local calendar dates, daylight saving/time-zone changes, leap years, and midnight boundaries.
- [ ] Audit autosave durability and prevent data loss when navigating away or the app is killed.
- [ ] Review database query performance and large lists on low-memory devices.
- [ ] Add a central, user-friendly error-handling strategy that avoids swallowing failures or exposing raw native errors.
- [ ] Check app startup, memory, battery usage, and responsiveness on low/mid-range hardware.
- [ ] Create a device test matrix and record OS version, device, steps, expected/actual result, and build commit.

**Gate:** critical feature suite passes; no known data-loss or release-blocking defects; accessibility review findings resolved or documented with rationale.

### P1 — Privacy, security, and open-source governance

- [ ] Add a clear privacy policy matching actual behavior and permissions, including Accessibility and Usage Access; do not claim data is never read when those opt-in features require access to on-screen app content or usage statistics.
- [ ] Add an appropriate open-source license after choosing terms and confirming any third-party asset/dependency licensing.
- [ ] Add a security reporting policy and issue template for reproducible bug reports.
- [ ] Confirm there are no analytics, advertising, cloud, or network services unless intentionally introduced and documented.
- [ ] Avoid logging note/task content, usage histories, accessibility text, backup data, or secrets.
- [ ] Verify Android manifest permissions and exported components are minimal and intentional.
- [ ] Check native config plugins are idempotent across repeated clean prebuilds and fail loudly when expected project anchors change.
- [ ] Add a data retention/deletion explanation and confirm local data deletion semantics.
- [ ] Document supported Android versions and any known device-specific limitations.

**Gate:** permission disclosures match implementation, no secret/personal data is logged, licence is clear, native declarations reviewed, and privacy claims are testable.

### P2 — Store/release readiness

- [ ] Finalize app name, icon/adaptive icon, screenshots, concise and full descriptions, support contact, and privacy policy URL.
- [ ] Review current Google Play target API, data safety, accessibility-service policy, prominent disclosure/consent, and app-content requirements before submission.
- [ ] Validate the signed bundle/artifact through the intended distribution channel and test update installation over the previous public build.
- [ ] Define semantic versioning and release notes, beta feedback process, rollback path, and compatibility policy.
- [ ] Provide installation/update instructions and explain backup precautions before uninstalling.
- [ ] Verify all release links, checksums, source tag, and build commit are consistent.

**Gate:** store-policy check is complete for the current submission date, signed release update installs cleanly, and release assets/documentation are correct.

## Suggested execution order

1. Stabilize CI, dependency lockfile, versioning, and canonical release workflow.
2. Test/repair SQLite migrations and backup/restore safety.
3. Test focus timer and notifications on real devices.
4. Test Accessibility blocking, UsageStats, and widgets; keep unproven behavior marked experimental.
5. Expand automated tests and perform accessibility/privacy/security reviews.
6. Complete licensing, privacy policy, store disclosures, signed release setup, and final release candidate testing.

## Release decision template

Do not call the app production-ready until each P0 gate is completed and evidence is recorded. Any feature that cannot meet its gate should be removed from the production scope or explicitly labelled experimental without compromising the core app. A build workflow passing only proves the checks included in that workflow passed.
